# EasyServer 0.2.0

Released: **2026-08-16**

EasyServer `0.2.0` made the interactive TUI the preferred human-facing entry point while preserving the CLI as the explicit automation/advanced-command surface.

It also moved the Provider Plugin SDK and both first-party plugins onto the `0.2.x` compatibility line, expanded the public provider-interaction/help contracts, and hardened connection recovery and SSH trust after real provider acceptance.

This page is historical release documentation. For current usage, start at [Getting started](../getting-started.md) or the [documentation index](../README.md).

## Highlights

### Task-first interactive TUI

Plain `easyserver` opens the TUI on an interactive terminal. The main user path is organized around:

- **Rent a server**;
- **Servers**;
- **Connections**;
- **Settings & Support**.

Working pages use a focused breadcrumb layout, contextual Actions, and one arrows/Enter/Esc interaction model rather than exposing internal subsystems as peer tabs.

Installed Provider Plugins that advertise EasyServer package metadata can be selected by human display name without importing an unconfigured provider runtime just to populate the picker.

Provider-specific acquisition remains provider-owned: Vast.ai keeps its marketplace/filter/rental model, while Intelion.cloud keeps its server catalog/configurator model.

### More usable server connections

The normal Connect flow asks for the remote **application/service port**, not the SSH transport port, and can choose the provider-declared connection method automatically.

Connections presents local addresses rather than requiring users to understand Access Method, Session, daemon, or saved-intent internals up front.

Recovery became cause-specific and in-place:

- local port conflict → edit local port;
- SSH works but service port is unavailable → edit service port;
- retryable late transport/auth failure → retry the retained connection request;
- first-use SSH trust → review exact fingerprint evidence;
- saved background connection waiting on trust → review the fingerprint and retry that same saved definition.

SSH connection messaging separates provider API authentication, SSH login authentication, changed host identity, fingerprint-discovery failure, SSH transport failure, server-side TCP-forwarding policy, and remote application/service reachability.

If `ssh-keyscan` cannot obtain first-use host-key evidence, EasyServer can use a bounded isolated OpenSSH handshake for observation only. Permanent trust still requires explicit approval and fresh exact revalidation.

### Diagnostics and constrained terminals

Diagnostics now opens with a concise summary and provides a dedicated scrollable report viewer. Copy uses the same sanitized payload being reviewed, and screen-reader mode receives the complete report linearly.

The TUI supports narrow terminals, `NO_COLOR`, and Ink screen-reader mode while keeping focused/actionable content reachable.

### Machine-readable CLI contract

Automation can prefix a named command with `--json` to receive envelope schema version `1`.

Successful commands emit one `{ schemaVersion, ok: true, data }` document on stdout. Terminal failures emit one `{ schemaVersion, ok: false, error }` document on stderr with a non-zero exit status.

First-use SSH trust can expose structured host/key evidence. A separate `host-trust approve` command authorizes exactly that evidence after revalidation, allowing non-interactive automation to remain fail-closed.

See [Machine-readable CLI output](../cli-json.md) for the current `0.2.x` contract.

### Provider Plugin SDK 0.2.x

The `0.2.0` SDK added public contracts needed by the TUI and host-owned safety model, including:

- declarative credential descriptors/readiness metadata;
- billable/destructive risk metadata for provider mutations;
- structured provider command help and a dedicated side-effect-free `./easyserver-help` contribution;
- provider command result/handoff contracts for affected provider identities;
- presentation-neutral provider interactive flows;
- stricter provider identity/deletion semantics for inconclusive observations.

Provider-specific configuration/acquisition still belongs in Provider Features rather than EasyServer core.

## Compatibility changes from 0.1.x

### Plain `easyserver`

The intentional user-facing entry-point change was:

- `0.1.x`: plain `easyserver` could be treated as a command-mode invocation;
- `0.2.0`: plain `easyserver` opens the TUI on a supported interactive terminal.

Scripts that want help must use:

```powershell
easyserver --help
```

Named commands such as `plugins`, `instances`, `connect`, `daemon`, and `sessions` remain command-mode paths.

A no-argument non-interactive invocation fails clearly instead of emitting terminal-control output.

### Plugin compatibility line

The released package set was:

- `@easyai101/easyserver-plugin-sdk@0.2.0`;
- `@easyai101/easyserver@0.2.0`;
- `@easyai101/easyserver-plugin-vastai@0.2.0`;
- `@easyai101/easyserver-plugin-intelion@0.2.0`.

First-party packages/manifests use the `^0.2.0` compatibility line. A plugin declaring only `^0.1.0` does not claim compatibility with the `0.2.x` host/SDK.

### Local State and credentials

`0.2.0` did not require deleting/recreating valid EasyServer Local State. Valid `0.1.x` state remains readable, canonical instance identity is preserved, and opaque Secret References continue to address the OS-backed credentials.

The `0.2.x` line also added validated Local State recovery-generation behavior and crash-recoverable ownership metadata for newly created temporary SSH credential material on the qualified Windows path.

## Install this historical version

### npm

```powershell
npm install --global @easyai101/easyserver@0.2.0
npm install --global @easyai101/easyserver-plugin-vastai@0.2.0
# or
npm install --global @easyai101/easyserver-plugin-intelion@0.2.0
```

### GitHub Release

Release `v0.2.0` published:

```text
easyserver-0.2.0-windows-x64.zip
easyserver-0.2.0-SHA256SUMS.txt
```

The portable bundle contains the core CLI/runtime dependencies but not Node.js or Provider Plugins.

## Release environment

The `0.2.0` supported client target was:

- Windows 11 x64;
- Node.js `24.18.1`;
- npm `11.16.0` for npm/package installation;
- Windows OpenSSH Client for SSH-backed access.

Linux and macOS were not part of the `0.2.0` release support contract.
