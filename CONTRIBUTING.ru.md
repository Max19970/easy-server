# Участие в разработке EasyServer

**Язык:** [English](CONTRIBUTING.md) · Русский

Спасибо за помощь в развитии EasyServer. Изменения должны сохранять границы продукта, благодаря которым специфичное для провайдера поведение может развиваться внутри соответствующего плагина, а ядро не превращается в набор provider-specific ветвлений.

## Подготовка окружения

EasyServer `0.2.x` разрабатывается и проверяется с Node.js `24.18.1` и npm `11.16.0`. Точная версия Node.js записана в `.nvmrc`.

Установите зависимости репозитория:

```powershell
npm ci
```

Перед отправкой существенного изменения выполните полный детерминированный release-level набор проверок репозитория:

```powershell
npm run release:check
```

Он включает typecheck, тесты, проверку содержимого публикуемых пакетов, установку собранных пакетов, поддерживаемую Windows TUI-поверхность и путь сборки/проверки release-артефакта.

Обычная разработка и проверка pull request не должны требовать реальных credential провайдеров или платных ресурсов. Live acceptance first-party провайдеров — задача мейнтейнера перед релизом, а не обычное требование к контрибьютору.

## Предложение изменений

- Перед созданием новой issue проверьте существующие задачи, чтобы не создавать дубликат.
- Сначала заведите issue, если изменение требует обсуждения продукта/архитектуры или добавляет нетривиальную новую возможность.
- Один pull request должен быть сфокусирован на одном связном результате.
- При изменении runtime-поведения добавляйте или обновляйте тесты на публичных behavioral seams.
- Не привязывайте тесты только к приватным helper-функциям или деталям реализации, которые могут измениться без изменения контракта.
- Специфичные для провайдера acquisition/product semantics должны оставаться внутри соответствующего плагина провайдера.
- Не добавляйте provider-specific поля и ветвления в ядро, если вариативность уже принадлежит Provider Feature/SDK seam.
- Обновляйте публичную документацию вместе с изменениями поведения, совместимости, настройки, безопасности или пользовательских сценариев.

Никогда не коммитьте API keys, пароли, приватные SSH-ключи, содержимое Secret Store, состояние реального acceptance-теста аккаунта или локальные machine-specific файлы разработчика.

## Изменения плагинов провайдеров

Начните с этих документов:

- [Создание плагина провайдера](docs/ru/plugin-authoring.md)
- [Контракты и эксплуатационная безопасность плагина провайдера](docs/ru/plugin-reference.md)
- [Минимальный пример Provider Plugin](examples/minimal-provider-plugin/README.md)

Плагины должны зависеть от публичного пакета `@easyai101/easyserver-plugin-sdk`, а не от исходников ядра EasyServer или deep import из внутренних путей.

Изменения, влияющие на совместимость, должны соответствовать [политике версионирования и совместимости](docs/ru/versioning-and-compatibility.md).

## Изменения документации

Публичная документация организована по задаче читателя и постепенно растущей технической сложности:

`README → Getting Started → тематические руководства → справка/политики → документация контрибьютора/плагинов → история релизов`

Вводные документы должны помогать решить ближайшую задачу. Плотные контракты следует помещать в справочные разделы, а не дублировать их в README и how-to руководствах.

Правила локализации описаны в [Documentation localization](docs/ru/localization.md). Английская документация остаётся канонической; переводы должны сохранять её публичные контракты и структуру.

Полная навигация находится в [индексе документации](docs/ru/README.md).

## Проблемы безопасности

Не сообщайте о предполагаемой уязвимости в публичной issue или pull request. Следуйте [SECURITY.ru.md](SECURITY.ru.md).
